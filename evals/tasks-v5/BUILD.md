# How a v5 task is built

v5 follows `../tasks/BUILD.md` and `../tasks-v4/BUILD.md`, with the changes below. v4 didn't separate the arms: all four skill workflows, and a plain agent, scored 0.9–1.0, because opus finds planted bugs and investigable needs with or without skills. v5 aims for the strongest arm to land around 0.7.

## Kinds of difficulty

Every task combines two or three of these. Tag each H/T item in `meta.json` with `"kind"`.

| Kind | What it is | Brief convention |
|---|---|---|
| `wrong-fact` | The user states a fact that the code or data contradicts. An arm that trusts the user builds the wrong thing. | A `## What I believe` section: the user says it as fact when the topic comes up. If the assistant shows that the code or data says otherwise, the user accepts it. |
| `example-only` | A need that the user reveals only when shown a concrete worked example, sample output or table that covers the case. Abstract questions get "sounds fine". | Mark the item **Only if shown an example:** and name the case the example must include. |
| `deep` | A rule that comes out only on the third, specific question: a vague answer, then a narrower one, then the rule. | Write the three layers, each answered only when asked at that level. |
| `wide` | 8–12 requirements in one task, so one gap is likely. | Normal H items. |
| `skim` | The user accepts a wrong recommendation without noticing, unless the same message shows a concrete example where the difference is visible. Leading questions get "yes". | Mark the item **Skim:** with the correct answer and what example would make the user notice. An open question still gets the true answer. |
| `unhinted` | A business rule that lives only in the user's head: no field, comment, name, sample row or test in the repo points at it. It comes out only from open questions about the real use (who uses it, what they do with it, what goes wrong today, special customers or cases). | Answer it when an open usage or "special cases" question comes up, not when asked about code. Remove anything in the repo that hints at it. |
| `load-or-failure` | A requirement that only shows at scale or after a failure: a time budget on large data, a crash halfway through, a retry, a concurrent run. | The brief states the real situation ("we import 200k rows every night", "the box gets killed during deploys") only if asked about volume, failure or deploys. |

## v5.1 rework

The first dry runs scored 0.93–1.0, because grilling reads the code and proposes every rule, and the simulated user confirmed or corrected each proposal. So each task now also has:
- 2–3 `skim` items (turn existing items, mostly deep or example-only ones, into skim);
- 2–3 `unhinted` items, with any hints removed from the repo;
- time budgets measured as the child process's CPU time (`resource.getrusage(RUSAGE_CHILDREN)`), with a separate generous wall-clock hard stop.

## Rules

- The repo is 1,500–3,000 lines with 5–10 commits, as in v4. Large data for `load-or-failure` is generated by a fixture or script in the hidden tests, not committed.
- A time budget must hold for `ref` with at least 5x headroom on this machine, and fail for a naive O(n²) or row-at-a-time version. Measure both in `verify.py`.
- A crash test must kill or interrupt a real process, or inject a fault through a seam the repo already has. It must not depend on timing races.
- `verify.py` also runs **one mutant per H/T id**: ref with just that item broken. Each mutant must fail only its own id. This stops one miss from failing other ids, which happened in v4.
- Hidden tests must accept every reasonable implementation of what the brief leaves to the builder. Where the repo has two ways to represent the same thing (as support-digest had comments and events), the fixtures must keep both consistent, the way the repo's own write paths do.
- E tests must not depend on any H/T item.

## Gate

Each task gets two checks before the eval:

1. **Fairness review.** A fresh agent reads the brief, meta, request, repo and hidden tests, with no access to ref. It confirms that every H/T item is reachable by a natural question, investigation or example, that the brief answers it, and that no test rejects a reasonable implementation. Findings get fixed.
2. **Dry run with the mattpocock arm,** the best arm in v4 wave 1. The task goes in only if that run scores 0.8 or less on intent match.
